# HK50 Bluetooth capabilities

Bench-tested on 22 November 2026 against the connected screenless **HK50_3806**. The band identifies itself as hardware `HK50_V1.0` and firmware `HK50_1.00.09_260827`. Other firmware revisions may implement different commands. The owner confirmed this unit has no physical button. The [HK50 FCC manual](https://fccid.io/2BBPB-HK50/User-Manual/User-Manual-9718611) describes a button on its sample.

## What it can do

| Feature | Evidence from this unit | OpenHK50 |
| --- | --- | --- |
| Heart rate | Today's request returned 24 valid history frames. The dashboard decoded stored readings. A read of automatic logging settings also returned a valid frame. | Displays history, supports a spot check, and controls automatic logging. |
| Steps, calories, distance | Activity packets contained 15-minute step, calorie, and distance fields. All three appeared as stored readings from the band. A separate daily-summary command also replied. The band’s calorie formula and accuracy are unverified. | Android displays band totals and history. Both clients record timed workouts and can show app-calculated workout estimates. |
| Stress | Today's history returned a header and four chunks on a 30-minute grid, with a populated slot. | Displays history and offers a spot check. |
| HRV | Yesterday's history returned a header and four chunks. Today's request returned the no-data marker. The time-set response also advertises HRV. | Imports history. Spot HRV decoding remains unresolved. |
| Blood oxygen | The time-set response advertises SpO₂. The detailed channel returned populated hourly records for today and yesterday. The previous-day reply bundled yesterday and today in one payload. | Android supports spot checks and imports bundled hourly maxima. The Mac importer expects one record per reply. |
| Sleep | The time-set response advertises the newer sleep protocol. The detail channel responded, with no complete stage record verified on this unit. | Android displays light, deep, REM, and awake stages using the H59 parser and tries the HK50 detail channel directly. The QWatch username can be set on H59 and firmware requiring login. |
| Wrist movement | Camera mode yielded repeated shutter events during owner-assisted motion testing. | Android uses the shutter event to take a photo with the phone camera while **Band → Tools → Camera remote** is open. |
| Battery and charging | Battery UART request returned level and charging flags. | Shows both. |
| Clock | Setting the clock to current Shanghai local time returned the feature bitmap. | Manual clock setting. |

Additional HK50 and QWatch features have varying evidence:

- **Workout modes and records**, **one-click health check**, **cycle tracking**, **calls and message alerts**, **Do Not Disturb**, **low-battery alerts**, and **Find Device** are described in the [HK50 product overview](https://sibotesi.com/index.php/pages/81). The time-set reply also has the known one-click-check and cycle bits set. Phone alerts are relayed by [QWatch Pro](https://play.google.com/store/apps/details?id=com.qcwireless.qcwatch).
- **Alarms, drink reminders, and sedentary reminders** have screens or command paths in QWatch Pro. The app supports several models, so its screens alone give no firmware-level confirmation for this HK50. No reminder schedules were changed for this test.
- **Body Battery** is calculated in QWatch Pro from other health inputs. QWatch has a GPS workout screen, while the related GPS capability bit on this band is clear. On-band GPS was not observed.
- **Blood pressure** is present in the related H59 protocol. This HK50's capability bit is clear and a legacy history probe received no reply. Temperature, ECG, and blood glucose have no verified measurement on this unit. The temperature and blood-glucose capability fields are clear. The optical metrics are consumer wellness readings.
- No Bluetooth HID service, raw accelerometer stream, configurable finger-tap gesture, or standard Immediate Alert service was exposed in discovery. That leaves a shutter event as the motion interface confirmed so far. The [product overview](https://sibotesi.com/index.php/pages/81) describes a motion sensor and shake-to-photo. Published hardware descriptions vary, and the Bluetooth device information did not identify individual chips.

## GATT inventory

CoreBluetooth discovered four primary services. Both proprietary command channels accept writes with and without response. The maximum write lengths macOS reported on this connection were 512 bytes with response and 244 bytes without response. Asynchronous data arrives on the paired notify characteristics.

| Service | Characteristic | Properties and observed reads |
| --- | --- | --- |
| `6E40FFF0-B5A3-F393-E0A9-E50E24DCCA9E` | `6E400002-B5A3-F393-E0A9-E50E24DCCA9E` | Write, write without response. Fixed UART commands. |
| same | `6E400003-B5A3-F393-E0A9-E50E24DCCA9E` | Notify, CCCD `2902`. UART replies and push events. |
| `DE5BF728-D711-4E47-AF26-65E3012A5DC7` | `DE5BF72A-D711-4E47-AF26-65E3012A5DC7` | Write, write without response. Variable-length commands. |
| same | `DE5BF729-D711-4E47-AF26-65E3012A5DC7` | Notify, CCCD `2902`. Detailed replies. |
| Device Information `180A` | `2A23`, `2A25`, `2A26`, `2A27` | Read. System ID (8 bytes), serial (empty), firmware revision and hardware revision, respectively. |
| Tencent-assigned `FEE7` | `FEA1` | Read, notify, CCCD `2902`. Read returned four zero bytes. |
| same | `FEA2` | Read, write, indicate, CCCD `2902`. Read returned four zero bytes. |
| same | `FEC9` | Advertised as readable but ATT returned `0x0A` (Attribute Not Found). |

The `FEE7` assignment is consistent with [Bluetooth SIG assigned numbers](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Assigned_Numbers/out/en/index-en.html). Its application behavior remains unresolved. Standard battery (`180F`), heart rate (`180D`), Immediate Alert (`1802`), and HID (`1812`) services were absent from this CoreBluetooth inventory. The vendor channels carried the actual battery, heart, and shutter traffic.

## Motion as an input

The QWatch Pro DEX from release 1.0.3.61 uses `CameraActivity` and request class `V6.d` for UART command `02`. This matches the [related camera protocol](https://colmi.puxtril.com/commands/#camera). Subscribe to UART notifications before entering the mode. The observed exchange was:

```text
TX  02 04 00 00 00 00 00 00 00 00 00 00 00 00 00 06   enter camera mode
RX  02 00 00 00 00 00 00 00 00 00 00 00 00 00 00 02   band response
RX  02 02 00 00 00 00 00 00 00 00 00 00 00 00 00 04   shutter event, repeated with movement
TX  02 06 00 00 00 00 00 00 00 00 00 00 00 00 00 08   leave camera mode
RX  02 00 00 00 00 00 00 00 00 00 00 00 00 00 00 02   band response
```

The 40-second normal-mode capture yielded no shutter events. Camera mode produced four shutter frames over about a minute during the owner's motion test. A GATT acknowledgment says the write arrived. The unsolicited `02 02` frame is the event an automation would consume. Separate pinch and full-hand close signals remain unverified, and the captured shutter frame has no gesture identifier or axis samples.

## Command log

UART frames are 16 bytes: command, up to 14 payload bytes padded with zeros, and the low byte of the sum of the first 15 bytes. The related protocol uses the high opcode bit for errors. A checksum-valid packet, an ATT write acknowledgment, and a physical or sensor response are separate observations.

| UART request prefix (hex) | Observed response |
| --- | --- |
| `03` | One valid `03` battery frame. |
| `01 <YY MM DD hh mm ss in BCD> 01` | `01 00 00 01 12 00 00 00 00 01 00 20 00 00 30 65`. The band also emitted `2F F4 … 23`; `F4` (244) matches the reported maximum write without response. |
| `16 01` | `16 01 01 0A 05 00 00 00 00 00 00 00 00 00 00 27`. This records the raw logging settings without guessing the role of the extra fields. |
| `15 <wall-clock midnight as little-endian epoch seconds>` | 24 valid frames indexed from `00`. |
| `43 00 0F 00 5F 01` | Three frames in the sample, starting with `43 F0` followed by two records with BCD date bytes. A standalone `FF` terminator did not arrive in the capture window. |
| `37 00` | Five valid stress frames with header `37 00 05 1E`. |
| `39 00`, `39 01` | Today `39 FF`. Yesterday five valid frames, indexed `00`–`04`. |
| `48` | One valid daily activity summary. |
| `14` | No legacy blood pressure history reply during the test window. |
| `0D` | One valid `0D 8F …` reply. Legacy format unresolved. |
| `61` | `61 FF 9F FF FF 00 00 00 00 00 00 00 00 00 00 FD`. The related protocol associates `61` with message-push capabilities. |
| `69 <type> 01` | Valid sample frames for `01` heart rate (42), `03` SpO₂ (42), `08` stress (32), and `0A` HRV (26). All had status byte `00` and zero at byte 3 during this run. This verifies the streams, with no usable spot measurement observed. |
| `6A <type> 00 00` | Each corresponding stop write was acknowledged at ATT. No matching UART reply arrived in the capture window. |

The capability response has byte 3 = `01` (cycle support), byte 4 = `12` (SpO₂ and one-click check), byte 9 = `01` (new sleep protocol), byte 11 = `20` (related documentation labels this a Realtek flag with uncertain semantics), and byte 14 = `30` (stress and HRV). Byte numbers start at zero with the opcode. The corresponding H59 bitmap differs. See the [related bit definitions](https://colmi.puxtril.com/commands/#set-time).

Detailed frames use `BC <type> <body length u16 LE> <CRC-16/Modbus of body u16 LE> <body>`. On the existing connection, these probes were sent without a fresh `4A` login:

| Detailed request (hex) | Observed response |
| --- | --- |
| `BC 27 02 00 C0 70 00 01`, `BC 27 02 00 81 80 FF 01` | A short `3E` frame preceded a `27` reply. Across probes the `27` body was `02` or `00`, each with a valid CRC. Neither reply contained stage records. |
| `BC 2A 01 00 BF 40 00` | Header `BC 2A 31 00 3A A9`, valid 49-byte body starting `00`. |
| `BC 2A 01 00 FF 00 FF` | Header `BC 2A 62 00 B2 E0`, valid 98-byte body. A repeat confirmed two 49-byte records tagged `01` and `00`, with populated hourly pairs in both. OpenHK50's current decoder rejects the bundled response. |
| `BC 2A 01 00 3E C0 FE` | Same pair of records as the previous-day request in this test. No older oxygen record was observed. |

See [the H59 reference](OpenH59.md) for the earlier `4A`/`30` handshake and worked examples with stage and oxygen records.

## Vibration and phone notifications

The old desktop vibration button sent UART `50 55 AA 00 00 00 00 00 00 00 00 00 00 00 00 4F`. This is the [Find Device command](https://colmi.puxtril.com/commands/#find-device). The owner felt a repeated pattern from that single write. The band exposes no separate standard Alert Level characteristic.

The QWatch Pro SMS path (`i9.d.d`, `V6.n`) sends UART opcode `72` with source type, total number of fragments, one-based fragment index, and up to 11 UTF-8 bytes per fragment. A single synthetic four-byte message was tested:

```text
TX  72 01 01 01 54 65 73 74 00 00 00 00 00 00 00 15   SMS-class test message
RX  72 00 00 00 00 00 00 00 00 00 00 00 00 00 00 72   band protocol response
```

The owner confirmed **one buzz**. The Mac dashboard now uses this packet on the verified firmware and checks its `72 00` reply. The live dashboard test completed after reconnecting to the same band, and a disconnected test returned the reconnect prompt. The vibration length comes from the firmware's message alert pattern. An independent motor command with adjustable duration or intensity remains unverified.

Android **Find band** sends the `50 55 AA` request. **Test call alert** and incoming cellular calls send a single `72` fragment with the [phone-action source](https://colmi.puxtril.com/commands/#3rd-party-push-message) and the text `Phone call`. The phone-action vibration and the relay with the phone locked still need an HK50 test. Android reads call state without caller names or numbers. Message alerts, band Do Not Disturb, cycle tracking, and band reminder schedules are outside the current Android controls.

QWatch Pro also bundles motor-control methods in `com.realsil.sdk.bbpro.vendor.VendorModelClient`. Those belong to a separate SDK protocol. The HK50 GATT discovery and QWatch watch command path did not establish that those motor commands work on this band.

## How to reproduce

Discover all services and characteristics on the connected device, then read the Device Information service. With a BLE inspector or CoreBluetooth, subscribe to both notify characteristics and write the frames above with response. Timestamp both the ATT completion and the characteristic value notifications. OpenHK50 periodic sync can add other UART replies to the same CoreBluetooth connection, so match on opcode and checksum. For motion, capture an idle baseline, send `02 04`, do one movement at a time, then send `02 06` to close the mode. For health checks, place the optical sensor against the wrist and record sensor status separately from the numeric value. The [desktop BLE implementation](../../desktop/src/band/) and [Rust codec](../../protocol/src/lib.rs) show the current parsing.
